System Configuration

Single Source of Truth for all CRLD System Parameters

18 sections, 40+ CONFIG keys, all numeric thresholds, behavioral switches, and project paths centralized in one document

Core Principle: All numeric thresholds, limits, budgets, and behavioral switches in the system derive from this file. When a value changes here, it propagates to every consumer via {{CONFIG: section.parameter}} inline syntax.

Configuration Resolution Chain (§1.1)

1.
System_Configuration.md
Single source of truth — all defaults live here
2.
Engines
Reference CONFIG keys and define what parameters mean (scoring bands, thresholds, weights)
3.
Pipelines
Reference CONFIG keys at phase boundaries (iteration limits, timeouts, gate options)
4.
Orchestrators
Resolve CONFIG values at dispatch time, pass to agents as dispatch parameters
5.
Role Agents
Do NOT load System_Configuration directly — receive resolved values from orchestrator dispatch payload

§17

Configuration Change Protocol

Governance for parameter updates
  1. Proposal: Team member proposes change via CHANGE_PROPOSAL
  2. Impact analysis: Identify all parameter consumers
  3. Gate 1: Technical review (breaks pipeline logic?)
  4. Gate 2: Human approval (system maintainer sign-off)
  5. Application: Update this file, values auto-inherit
Immutability: Values are immutable within single pipeline execution. New values apply to next invocation only.
